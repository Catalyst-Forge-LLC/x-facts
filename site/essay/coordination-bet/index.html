Why labels

Before you trust an app, model, tool, agent, or skill, you should be able to read the facts that matter in under a minute.

For people who use or publish the AI stack · Catalyst Forge · August 2026

You already do this with food. The box has a nutrition label. Not a novel. Not a press release. A short list of facts that change whether you put it in the cart.

The AI stack mostly still asks you to decide from READMEs, marketing pages, model cards of uneven quality, and marketplace blurbs. Optional tool annotations exist and almost nobody sets them. When you attach an MCP server, install a skill, pick a model, or let an agent run on a real workspace, the question is the same every time:

What are the objective facts that change whether I should trust this right now?

xFacts is a family of small nutrition-style labels for that moment. One label per layer. Same idea each time: structured facts you (or your tools) can check, plus a short human skim. When something important is not disclosed, the file says so instead of going quiet.

Five questions, five labels

  • AppFacts · body What is this app built from?
  • ModelFacts · brain What went into this model?
  • ToolFacts · toolbelt What does this instrument touch when invoked?
  • AgentFacts · hands What may this actor do, and on what leash?
  • SkillFacts · playbook What will this teach my agent to do?

A serious product can publish more than one. The app, the model it thinks with, the tools it wields, the agent configuration, the skills it installs. That full panel is clearer than any single landing page.

How to use a label

  • Skim the nutrition face for the decision in front of you: write access, network, leash, egress, and so on.
  • Prefer undisclosed over guesswork. Silence is information. If a publisher will not say what leaves the machine, treat that as a signal.
  • Compare like with like. The fields use shared vocabularies so two tools or two agents can sit side by side.
  • If you ship software, put the label next to the thing people adopt: the repo, the MCP server, the skill package, the shipped agent config.
  • If you build with agents, point them at the label files and schemas. Marketing HTML is the wrong place to learn the facts.

What a label is not

A label is not a certificate. Anyone can author one. A wrong claim that a tool has no side effects is worse than no label at all. Treat published facts as claims you can validate and diff, not as a blessing from a central authority.

A shareable card or QR (the portable viewer on each site) is a convenient way to pass a label around. It is not the source of truth. Prefer the file in the repo, checked against the public schema, when the stakes are real.

Specs and schemas are public domain (CC0). You can adopt the format without asking. Tooling is MIT. The suite grows only when a new label earns its place: someone adopts the thing, the facts are objective, and nothing better already answers the question.
